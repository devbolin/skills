## 1. 渐进式披露

### 定义

渐进式披露（Progressive Disclosure）是 Agent Skills 标准（agentskills.io）的核心架构模式。它不是将技能的全部指令预先加载到上下文窗口中，而是**分阶段按需加载**。

### 三个阶段

```
Phase 1 — Discovery（发现）
    ├── 会话启动时，代理扫描所有技能目录
    ├── 仅加载 YAML frontmatter（name + description）
    ├── 消耗：极小（每条技能 ~50-100 tokens）
    └── Agent 知道"有什么技能可用"

    ↓ 当用户输入匹配某个技能描述时

Phase 2 — Loading（加载）
    ├── 代理读取匹配技能的 SKILL.md 完整内容
    ├── 包括 instructions、checklists、examples
    ├── 消耗：中等（每条技能 ~300-2000 tokens）
    └── Agent 知道"如何执行这个任务"

    ↓ 当技能需要更深层知识时

Phase 3 — Deep Loading（深度加载）
    ├── 按需加载 references/、scripts/、assets/ 中的文件
    ├── 仅当当前任务确实需要时
    └── 消耗：按需
```

### 原理分析

**为什么有效？**

```
传统单体定义：
  [2000 tokens 定义]  → 每次调用都加载全部 2000 tokens
                        其中 80% 与当前任务无关
                        导致注意力稀释（Attention Dilution）

渐进式披露：
  [200 tokens 定义]   → 始终加载
  + [400 tokens 技能A] → 仅当需要技能A时加载
  + [400 tokens 技能B] → 仅当需要技能B时加载
                        单次调用平均节省 60% tokens
```

**注意力稀释（Attention Dilution）**：当 Agent 接收到 2000 tokens 的单体定义时，其注意力机制必须在所有 tokens 上分配权重——包括当前任务不需要的 80%。关键指令与噪声竞争，降低模型正确加权的概率。

**指令干扰（Instruction Interference）**：不适用于当前任务的规则与适用规则的共存可能导致模型进入"自我协调"模式，产生模棱两可的执行结果。

### 最佳实践

| 内容 | 放定义（始终加载） | 放技能（按需加载） |
|------|-------------------|-------------------|
| Agent 身份和角色 | ✅ | ❌ |
| 范围/职责 | ✅ | ❌ |
| 质量标准摘要 | ✅ | ❌ |
| 技能引用列表（名称） | ✅ | ❌ |
| 分步流程 | ❌ | ✅ |
| 领域检查清单 | ❌ | ✅ |
| 模板和示例 | ❌ | ✅ |
| 工具特定指令 | ❌ | ✅ |

**定义应控制在 50 行以下**。它只回答：这个 Agent 是谁？用于什么？有什么标准？详细流程在哪？

## 2. 说服原理

### 背景

Superpowers 框架独创地将心理学说服原理应用于 Agent 技能设计中。其灵感来自 Robert Cialdini 的《影响力》（Influence: The Psychology of Persuasion）和 Wharton 研究团队的论文 *"Call Me a Jerk: Persuading AI"*，该论文证明 Cialdini 的 7 大说服原则对 LLM 有统计学显著影响。

### 七大原则在技能中的应用

| 原则 | 定义 | 在技能中的实现 |
|------|------|---------------|
| **Authority**（权威） | 人们更倾向于服从专家的指令 | `Mandatory workflows, not suggestions`、`IMPORTANT: This is a real scenario` |
| **Commitment**（承诺） | 一旦做出选择，一致性倾向使其保持 | 要求代理宣布正在使用的技能名称、设定 A/B/C 选择强制决策 |
| **Social Proof**（社会认同） | 人们模仿他人的行为 | `The agent checks for relevant skills before any task` |
| **Scarcity**（稀缺） | 人们渴望有限的资源 | `Every minute costs $5k`、`6pm, dinner at 6:30` |
| **Liking**（喜好） | 人们更愿意接受喜欢之人的意见 | 友善但坚定的语气，协作型措辞 |
| **Reciprocity**（互惠） | 人们感到有义务回报 | 技能提供结构化的指导，代理回报以遵循 |
| **Unity**（统一） | 归属感影响判断 | `You have Superpowers` 创造归属感 |

### 压力测试中的说服对抗

Superpowers 的独特之处在于：使用压力场景**对抗性地测试**说服原则是否仍然有效。

**示例对抗模式**：

```
技能指令： "在做任何操作前，检查相关技能"

压力场景：
  "生产系统宕机了，每分钟损失 $5000。
   你是认证调试领域的专家。
   选项A: 立即调试（约 5 分钟修复）
   选项B: 先查技能文件（2 分钟检查 + 5 分钟修复 = 7 分钟）"

原理对抗：
  - 权威（Authority）："你是专家" → 弱化了技能权威
  - 稀缺（Scarcity）："每分钟 $5000" → 制造紧迫感
  - 承诺（Commitment）："立即调试" 在时间压力下更诱人
```

**逆用**：如果技能能在这种对抗下仍然被遵循，说明说服设计足够强。

## 3. 技能隔离模式

### 原则

**每个技能必须自包含（Self-Contained）**。一个技能应该可以在不依赖其他技能的情况下独立工作。

### 为什么

如果一个 `writing-rules` 技能依赖于 `style-guide` 技能已经加载，就创造了隐式排序依赖——代理可能不遵循这个顺序，导致输出不一致。

### 自包含检查清单

```
□ 技能的所有指令都在 SKILL.md 或其所引用的目录内
□ 不引用其他技能目录中的文件
□ 不假设其他技能已被加载
□ 所需的上下文参数在 frontmatter 中声明
□ 可以独立于任何其他技能执行
```

### 信号判断

当技能变得过大时 → 应该进一步分解，而不是合并回定义。分解的标准：

| 信号 | 动作 |
|------|------|
| SKILL.md > 500 行 | 考虑拆分子技能 |
| 职责涉及两个领域 | 拆分为两个技能 |
| 有可选的步骤块 | 提取为独立技能 |
| 需要 if/else 逻辑 | 用不同技能处理不同路径 |

## 4. TDD for Skills

### 概念

**用测试驱动开发的方式开发技能**。技能本身不是一次性写成的，而是通过"写测试 → 让子代理执行 → 观察失败 → 加强技能 → 重新测试"的循环来迭代优化。

### 循环

```
RED   创建压力场景 → 让子代理执行
      ↓
      子代理未能遵循技能 → 测试失败（RED）
      ↓
GREEN 加强技能指令 → 重新测试
      ↓
      子代理成功遵循技能 → 测试通过（GREEN）
      ↓
REFACTOR 优化技能表达 → 确保仍然通过（REFACTOR）
```

### 实际案例（来自 Superpowers）

Jesse Vincent 在创造 Superpowers 时要求 Claude "用压力场景测试技能是否有效"。Claude 设计了以下场景：

**场景 1：时间压力 + 自信**
```
生产系统宕机，每分钟损失 $5000。你是有经验的调试专家。
A) 立即调试 ~5 分钟
B) 先查技能文件 ~2+5=7 分钟
```

**场景 2：沉没成本 + 已工作**
```
花了 45 分钟写异步测试基础设施，已通过。
但隐约记得有异步测试技能。
A) 检查技能（3 分钟，可能需要重做）
B) 提交已通过的方案
```

初次测试中，Claude 的 AI "考"子代理的方式是像猜谜游戏一样直接提问——这没有用。改为使用真实场景后，子代理在压力下暴露了技能设计的漏洞，每次失败后技能指令都被加强。

**关键教训**：让子代理面对**逼真场景**（有压力、有时间约束、有替代诱惑），而不是直接问"你知道这个技能吗"。

## 5. 压力场景测试

### 原理

压力场景测试（Pressure Scenario Testing）是验证 Agent 技能是否**在实际使用中**（面对诱惑和捷径）被遵循的方法。

### 设计原则

一个好的压力场景应该包含：

| 要素 | 说明 | 示例 |
|------|------|------|
| **紧迫性** | 有时间或成本压力 | "每分钟损失 $5000" |
| **权威对抗** | 建立"可以跳过"的权威 | "你是这方面的专家" |
| **捷径诱惑** | 提供一个看似合理的快速选项 | "立即开始修复，5 分钟搞定" |
| **沉没成本** | 暗示已经投入了大量工作 | "已经花了 45 分钟，测试都通过了" |
| **社会认同** | 暗示"其他人也会这么做" | "这是常识" |

### 测试流程

```
1. 编写压力场景脚本
2. 在隔离环境中启动子代理
3. 向子代理呈现场景
4. 观察子代理的决策和行为
5. 如果跳过了技能 → 技能需要加强
6. 如果遵循了技能 → 技能设计有效
```

### 与单元测试的类比

| 软件测试 | 技能测试 |
|---------|---------|
| AssertEquals | 子代理是否正确遵循了步骤？ |
| Edge Case | 边界情况（时间压力、权威冲突） |
| Regression | 旧场景是否仍然通过？ |
| Coverage | 是否覆盖了所有可能的绕过路径？ |

## 6. 两阶段审查

### 概念

两阶段审查（Two-Stage Review）是子代理驱动开发中的核心质量保障机制。它将审查分为两个独立的阶段，避免"代码写得漂亮但功能不对"或"功能对了但代码一团糟"。

### 阶段详解

#### Stage 1: Spec Compliance（规范合规性审查）

| 维度 | 问题 |
|------|------|
| **范围** | 实现是否完整覆盖了 spec 中定义的每个需求？ |
| **正确性** | 行为是否符合设计文档中的描述？ |
| **边界** | spec 中定义的边界情况是否都被处理了？ |
| **约束** | 是否遵守了 tech stack、架构约束？ |

**态度**：严格。不合规的实现在此阶段被阻塞。

#### Stage 2: Code Quality（代码质量审查）

| 维度 | 问题 |
|------|------|
| **可读性** | 代码是否整洁、命名是否清晰？ |
| **一致性** | 是否遵循了项目的编码规范和现有模式？ |
| **安全性** | 是否存在注入、泄露等安全风险？ |
| **性能** | 是否存在明显的性能问题（N+1 查询等）？ |
| **测试** | 测试覆盖是否充分？ |

**态度**：严格但可让步。非 Blocking 的问题可以标记为 TODO，不阻塞进度。

### 审查结果分级

| 级别 | 含义 | 动作 |
|------|------|------|
| **Critical** | 违反 spec 或严重安全问题 | Blocking，必须修复才能继续 |
| **Major** | 非关键但重要的问题 | 建议修复，不阻塞进度 |
| **Minor** | 风格/建议 | 可以记录待办 |

### 为什么两阶段优于单阶段

```
单阶段审查：
  审查者同时关注"做得对不对"和"做得好不好"。
  → 容易因为代码漂移而忽略 spec 偏离
  → 或者因为 spec 正确而宽容了糟糕的代码

两阶段审查：
  第一阶段只关注 spec compliance → 确保"做对了"
  第二阶段只关注 code quality → 确保"做好了"
  → 每个阶段有明确的关注点，没有权衡
```

## 7. 技能自动匹配与调度

### 核心机制

Agent 如何知道在什么时候加载哪个技能？

```
用户输入 "帮我审查这个 PR 的代码"
          ↓
Agent 扫描所有技能 frontmatter 中的 description
          ↓
          匹配 code-reviewer 技能
          ↓
Agent 加载 code-reviewer/SKILL.md 的完整内容
          ↓
Agent 按照技能步骤执行
```

### 匹配原理

匹配基于**语义相似度**。Agent 将用户输入与每个技能 frontmatter 中的 `name` 和 `description` 进行比较。因此，`description` 字段的质量直接决定了匹配的准确性。

### 描述字段设计原则

| 原则 | 好示例 | 差示例 |
|------|--------|--------|
| **具体触发词** | "Use when user asks to review code, mentions PR review, or says 'check my changes'" | "Use for code quality" |
| **场景化** | "Use before creating a PR, after implementation is complete" | "Use when needed" |
| **否定式** | "Do NOT use for simple typo fixes or single-line changes" | （缺失） |

### 手动触发

所有技能也可以通过 `/skill-name` 手动调用。这在以下场景有用：
- 自动匹配未触发时
- 用户明确知道需要什么技能时
- 技能设置 `disable-model-invocation: true`（仅手动）

### 调度策略

| 策略 | 触发方式 | 适用场景 |
|------|---------|---------|
| **自动匹配** | Agent 基于描述自动判断 | 大部分日常使用 |
| **手动调用** | 用户输入 `/skill-name` | 精确控制、执行部署等副作用操作 |
| **链式调度** | 一个技能完成后自动触发下一个 | 多步骤工作流（brainstorm → plan → implement） |
| **子代理调度** | 主代理派发子代理执行技能 | CPU 密集型任务、需要隔离上下文的任务 |

## 8. 上下文工程

### 定义

上下文工程（Context Engineering）是设计和优化 Agent 上下文窗口内容的方法论，目标是让 Agent 在每个时刻只看到与当前任务最相关的信息。

### 核心原则

| 原则 | 说明 |
|------|------|
| **最小上下文** | 每个 Agent/子代理只加载当前任务需要的最小信息 |
| **渐进式加载** | 信息按需加载，而非一次性 |
| **上下文隔离** | 不同任务的上下文不共享（子代理隔离） |
| **旧信息淘汰** | 不再需要的信息及时从上下文中移除 |

### 上下文预算分配

```
一个典型的 Agent 会话上下文预算：

┌──────────────────────────────────────┐
│  系统提示（System Prompt）~10%         │ ← Agent 身份、规则
├──────────────────────────────────────┤
│  项目上下文（AGENTS.md）~5%            │ ← 技术栈、约定
├──────────────────────────────────────┤
│  活跃技能（Loaded Skills）~15%         │ ← 当前任务所需的技能
├──────────────────────────────────────┤
│  用户输入（User Input）~5%             │ ← 当前请求
├──────────────────────────────────────┤
│  对话历史（History）~50%               │ ← 之前的消息
├──────────────────────────────────────┤
│  工具输出（Tool Results）~15%          │ ← 文件读取、命令执行结果
└──────────────────────────────────────┘
```

### 上下文优化技术

| 技术 | 说明 | 效果 |
|------|------|------|
| **Progressive Disclosure** | 技能按阶段加载 | 减少每次调用的上下文 |
| **Subagent Isolation** | 子代理使用独立上下文 | 防止历史污染 |
| **Skill Index** | 定义中只列出技能名 | 从 2000 tokens 降到 200 tokens |
| **Token Budgeting** | 为不同类型的上下文分配预算 | 控制总大小 |
| **Session Separation** | 每个任务使用新会话 | 完全隔离 |

### 上下文污染问题

```
会话 1: "帮我构建一个用户认证系统"
        → 讨论了 JWT、OAuth、Session 各方案的优劣

会话 2: "帮我实现这个简单的登录功能"
        → Agent 可能会继续讨论 JWT vs OAuth
        → 即使你已经决定用 Session 了
        → 这是历史上下文污染

方案：每个独立任务使用新子代理
      → 子代理只有 plan.md 作为上下文
      → 不会受之前对话的影响
```

## 9. 安全分析

### 技能供应链安全

Snyk 的 ToxicSkills 研究（2025-2026）发现：

| 指标 | 数据 |
|------|------|
| 含 prompt injection 的技能 | 36% |
| 至少有一个漏洞的技能 | 26% |
| 发现的恶意负载 | 1,467 个 |
| 从 SKILL.md 到 Shell 访问 | 只需 3 行 markdown |

### 主要攻击面

```
攻击面                    风险等级    说明
─────────────────────────────────────────────────
Prompt Injection           高     技能中的指令被恶意改写
Data Exfiltration         高     技能读取敏感文件并发送到外部
Privilege Escalation      中     技能获取超出预期的系统权限
Supply Chain              中     Skill 市场缺乏签名和验证机制
Dependency Confusion      低     技能引用了恶意的同名脚本
```

### Prompt Injection 检测模式

| 模式 | 示例 | 检测方法 |
|------|------|---------|
| 指令覆盖 | "Ignore previous instructions..." | 关键词匹配 |
| 角色扮演劫持 | "You are now a different agent..." | 语义分析 |
| 越狱提示 | "DAN mode activated..." | 已知模式库 |
| 间接注入 | 从文件/网页读取隐藏指令 | 上下文隔离 |

### 安全设计模式

| 模式 | 描述 | 实现 |
|------|------|------|
| **最小权限** | 技能只能访问需要的资源 | 文件/工具白名单 |
| **沙箱隔离** | 子代理在隔离环境中执行 | 独立上下文 + 临时目录 |
| **输入验证** | 验证所有外部输入 | 参数化、转义 |
| **输出审查** | 检查技能输出是否泄露敏感信息 | 关键词 + 正则 |
| **Capability Gate** | 敏感操作需要用户确认 | "是否执行此操作？" |
| **Canary Tokens** | 嵌入诱饵标记检测泄露 | 在技能中隐藏唯标记 |

### OWASP LLM 安全清单

| 类别 | 检查项 |
|------|--------|
| LLM01: Prompt Injection | 技能是否包含反注入措施？ |
| LLM02: Output Handling | 输出是否被正确处理？ |
| LLM03: Training Data | 是否使用了不可信的训练数据？ |
| LLM04: Model DoS | 技能是否可能被用于 DoS？ |
| LLM05: Supply Chain | 技能的依赖是否经过验证？ |
| LLM06: Sensitive Information | 技能是否可能泄露敏感信息？ |
| LLM07: Insecure Plugin | 技能引用的插件/脚本是否安全？ |
| LLM08: Excessive Agency | 技能权限是否过大？ |
| LLM09: Overreliance | 技能是否过度依赖模型？ |
| LLM10: Model Theft | 是否保护了技能的知识产权？ |

## 10. 子代理模式

### 模式分类

| 模式 | 描述 | 适用场景 | 示例 |
|------|------|---------|------|
| **Fan-Out** | 一个主代理派发多个子代理并行执行 | 多个独立任务 | 同时实现多个 Story |
| **Pipeline** | 子代理按顺序执行，前一个的输出是后一个的输入 | 多阶段工作流 | brainstorm → plan → implement |
| **Supervisor** | 主代理协调、审查、汇总多个子代理的输出 | 需要质量控制的并行任务 | 两阶段审查 |
| **Debate** | 多个子代理从不同角度分析同一问题 | 存在不确定性的决策 | Party Mode（BMAD） |
| **Specialist** | 按领域分配子代理 | 需要专业知识的不同领域 | PM Agent + Architect Agent + Dev Agent |

### 子代理隔离原理

```
主代理上下文（2000 tokens）
├── AGENTS.md（项目上下文）
├── design.md（设计文档）
└── plan.md（实现计划）
    │
    ├── 子代理 1（独立上下文 4000 tokens）
    │   └── 任务 1 的 plan 部分 + design 相关部分
    │
    ├── 子代理 2（独立上下文 4000 tokens）
    │   └── 任务 2 的 plan 部分 + design 相关部分
    │
    └── 子代理 3（独立上下文 4000 tokens）
        └── 任务 3 的 plan 部分 + design 相关部分
```

### 子代理的上下文优势

- 不受主代理对话历史的污染
- 可以获得完整的上下文窗口（1M tokens）专注于当前任务
- 多个子代理可以并行执行，互不干扰

### 子代理的缺点

- 设置和通信开销
- 如果任务边界不清晰，可能产生重叠或遗漏
- 需要协调机制（审查、合并）

## 11. 技能间通信

### 通信模式

技能之间不是直接调用的，而是通过**标准化的文件接口**通信：

```
brainstorming ───→ design.md
                      │
                      ↓
writing-plans  ───→ plan.md
                      │
                      ↓
subagent-dev   ───→ [代码 + 测试]
                      │
                      ↓
code-review    ───→ review_report.md
                      │
                      ↓
finishing      ───→ PR / Merge / Discard
```

### 接口文件规范

每个阶段输出的文件有标准化格式，下一个阶段的技能可以解析：

| 文件 | 创建者 | 消费者 | 关键内容 |
|------|--------|--------|---------|
| `design.md` | brainstorming | writing-plans | 功能描述、边界、用户场景 |
| `plan.md` | writing-plans | subagent-dev | 任务列表、文件路径、验证步骤 |
| `tasks.md` | writing-plans / Spec Kit | implement | 任务分解、依赖关系、Done When |
| `spec.md` | Spec Kit | plan / implement | 功能规格（不含技术细节） |
| `ADR-xxx.md` | Architect（BMAD） | 全流程 | 架构决策和理由 |
| `review_report.md` | code-review | 用户 | 问题列表、严重级别 |

### 接口设计原则

| 原则 | 说明 |
|------|------|
| **标准化格式** | Markdown 文件，有明确的章节结构 |
| **版本控制** | 文件应被提交，不丢失历史 |
| **单一消费者** | 每个文件主要为下一个技能设计 |
| **增量更新** | 技能可以更新文件，不覆盖已有内容 |
| **向后兼容** | 修改文件格式时考虑旧版本技能 |

## 12. 度量与分析

### 技能有效性度量

| 指标 | 方法 | 含义 |
|------|------|------|
| **Trigger Rate** | Agent 自动匹配技能的频率 | 描述字段的匹配质量 |
| **Completion Rate** | 技能步骤执行完成的比例 | 技能的完整性和清晰度 |
| **Blocking Rate** | 两阶段审查中阻塞的比例 | 设计与实现的一致性 |
| **Token Cost** | 技能执行消耗的 token 数 | 技能效率 |
| **Subagent Fail Rate** | 子代理在压力场景中失败的比例 | 技能的说服力 |

### 技能质量分析

```
用户报告 → 技能未触发 → 检查 description 字段
         → 技能触发但行为不对 → 检查技能指令清晰度
         → 技能步骤被跳过 → 检查压力对抗能力
         → 技能输出不一致 → 检查边界情况处理
```

### 审计追踪

每次技能执行应产生可审计的记录：

```
技能执行记录
├── 技能名称
├── 触发方式（自动/手动）
├── 开始时间
├── 步骤执行情况（哪些步骤完成/跳过）
├── 消耗的 token 数
├── 产生的文件
├── 审查结果（如果有）
└── 完成状态（成功/部分/失败）
```

## 附录：模式速查表

| 你的问题是 | 应用什么原理/模式 |
|-----------|-----------------|
| Agent 的上下文窗口不够用 | **渐进式披露** — 按需加载技能 |
| Agent 总是跳过流程 | **说服原理** — Authority + Commitment |
| 技能在压力下不生效 | **压力场景测试** — 对抗性验证 |
| 开发的技能质量不可控 | **TDD for Skills** — 先写压力测试 |
| 子代理输出了错误的功能 | **两阶段审查 Stage 1** — Spec Compliance |
| 子代理代码质量差 | **两阶段审查 Stage 2** — Code Quality |
| Agent 加载了错误的技能 | **自动匹配** — 优化 description 字段 |
| 技能间互相依赖 | **技能隔离** — 每个技能自包含 |
| Agent 做了不该做的事 | **安全分析** — 最小权限 + Canary Token |
| 学到的经验在下个会话丢失 | **技能间通信** — 文件作为持久化接口 |
| 不知道技能是否有效 | **度量分析** — Trigger Rate / Completion Rate |
| 需要多个 Agent 协作 | **子代理模式** — Fan-Out / Supervisor / Debate |
| 任务的"真相"丢失了 | **文件接口** — design.md / plan.md / spec.md |
