## 1. 根因分析工具

解决"问题表面的症状 vs 根本的原因"这一永恒命题。

### 1.1 鱼骨图 / Ishikawa 图 / 因果图

| 属性 | 内容 |
|------|------|
| **提出** | 1943 年，Kaoru Ishikawa（石川馨） |
| **别名** | Fishbone Diagram, Cause-and-Effect Diagram |
| **用途** | 系统化地列出问题的所有可能原因，按类别组织 |
| **适用场景** | 质量缺陷、流程失效、生产事故 |

**结构**：

```
       Machine          Method           Material
          \              |               /
           \             |              /
            \            |             /
             ↘           |            ↙
    ──────────────────── Problem ────────────
             ↗           |            ↖
            /            |             \
           /             |              \
          /              |               \
       Measurement     Man            Environment
```

**经典 6M 分类**（制造业）：
- **Man**（人员）— 技能、培训、疲劳
- **Machine**（机器）— 设备故障、维护
- **Method**（方法）— 流程不合理、标准缺失
- **Material**（材料）— 材料缺陷、供应商
- **Measurement**（测量）— 测量误差、工具不准
- **Mother Nature**（环境）— 温度、湿度、噪声

**软件领域适配 5M**：
- **Man**（人）— 认知偏差、沟通失误、技能不足
- **Method**（方法）— 设计缺陷、流程漏洞
- **Machine**（工具）— IDE 问题、CI 故障、性能瓶颈
- **Material**（数据）— 数据质量问题、测试数据不足
- **Measurement**（度量）— 监控缺失、日志不足

---

### 1.2 5 Whys（5 问法）

| 属性 | 内容 |
|------|------|
| **提出** | 1930s，Sakichi Toyoda（丰田佐吉），Toyota Production System |
| **用途** | 通过连续追问"为什么"逐层深入根因 |
| **适用场景** | 单一根因的简单问题 |

**经典示例**：
```
1. 为什么机器停了？→ 保险丝过载
2. 为什么过载？→ 轴承润滑不足
3. 为什么润滑不足？→ 油泵没抽上油
4. 为什么没抽上？→ 油泵轴磨损
5. 为什么磨损？→ 没有安装过滤器，金属屑进入
```

**局限**：不适合多因复杂问题。建议配合鱼骨图使用。

---

### 1.3 原因-效果图 + 5 Whys 组合

最佳实践：先用鱼骨图列出所有可能原因类别，然后对每个候选原因追问 5 个 Why 找到根因。

---

### 1.4 变化分析（Change Analysis）

**用途**：当一个稳定系统突然出问题时，找出"什么变了"

**步骤**：
1. 描述问题（什么、在哪、何时、程度）
2. 与正常运行时的状态对比
3. 找出之间的差异
4. 评估每个差异是否是根本原因

---

### 1.5 故障树分析（FTA, Fault Tree Analysis）

**用途**：从顶级失效事件向下追溯到基本事件

**特点**：定量（可计算失效概率）+ 定性，层次结构，常用 AND/OR 门

**适用**：高风险系统（航空、核能、汽车安全）

---

### 1.6 屏障分析（Barrier Analysis）

**用途**：分析为什么防护机制（屏障）没有阻止问题发生

**三种屏障**：
- **物理屏障** — 防火墙、锁、护栏
- **管理屏障** — 流程、检查、培训
- **行为屏障** — 个人技能、注意力

## 2. 质量管理七大工具

由 Kaoru Ishikawa 提出，是全面质量管理（TQM）的基础工具集。

### 2.1 因果图（鱼骨图）

详见 1.1

### 2.2 检查表（Check Sheet）

| 用途 | 示例 |
|------|------|
| 收集数据、记录频率 | Bug 分类表、每日问题记录 |
| **格式** | 简单的表格 + 正字计数 |

### 2.3 控制图（Control Chart）

| 提出 | Walter Shewhart（1924） |
|------|------------------------|
| **用途** | 监控过程是否在统计控制范围内 |
| **要素** | 中心线（CL）、上控制限（UCL）、下控制限（LCL） |
| **软件应用** | 部署频率监控、错误率监控、响应时间监控 |

**模式判断**：
- 超出控制限 → 过程失控
- 连续 7 点在同一侧 → 趋势偏移
- 连续 7 点上升/下降 → 趋势变化

### 2.4 直方图（Histogram）

**用途**：显示数据分布，识别集中趋势和离散程度

**软件用例**：API 响应时间分布、Bug 修复时间分布

### 2.5 帕累托图（Pareto Chart）

| 提出 | Vilfredo Pareto（意大利经济学家），Juran 将其引入质量领域 |
|------|----------------------------------------------------------|
| **原理** | **80/20 法则**：80% 的问题由 20% 的原因造成 |
| **格式** | 柱状图（频次降序）+ 折线图（累计百分比）|
| **软件用例** | 哪种类型的 Bug 最多？先修那 20% 的关键类型 |

### 2.6 散点图（Scatter Diagram）

**用途**：研究两个变量之间的关系

**软件用例**：代码复杂度 vs 缺陷数、团队规模 vs 交付速度

### 2.7 分层图（Stratification）/ 流程图（Flowchart）

**分层**：按不同维度（时间、团队、模块、严重等级）拆解数据

**流程图**：将过程可视化，识别冗余、瓶颈、缺失环节

### 2.8 补充：新七大工具（1970s，日本 QC 研究会）

| 工具 | 用途 |
|------|------|
| 关联图法 | 理清复杂因素间的因果关系 |
| 亲和图法（KJ 法） | 从混沌信息中归纳分类 |
| 系统图法 | 目标-手段层级分解 |
| 矩阵图法 | 多维度交叉分析 |
| 矩阵数据分析法 | 数据量化的矩阵分析 |
| 过程决策程序图（PDPC） | 预测过程中的意外并准备对策 |
| 箭线图法 | 项目日程规划 |

## 3. 项目计划与进度工具

### 3.1 甘特图（Gantt Chart）

| 提出 | Henry Gantt（1910s） |
|------|---------------------|
| **用途** | 以时间为横轴，任务为纵轴的条形进度图 |
| **要素** | 任务、时间跨度、依赖关系、里程碑、进度百分比 |

**优点**：直观展示项目时间线和任务重叠
**缺点**：复杂依赖关系时不易看清

### 3.2 PERT 图（Program Evaluation and Review Technique）

| 提出 | 1950s，美国海军北极星导弹项目 |
|------|--------------------------------|
| **用途** | 分析任务依赖关系和关键路径 |
| **核心概念** | 关键路径（Critical Path）：决定项目最短工期的路径 |

**三点估算法**：
```
预期时间 = (乐观 + 4 × 最可能 + 悲观) / 6
```

**与甘特图的区别**：
- Gantt：展示时间线
- PERT：展示依赖关系

### 3.3 WBS（Work Breakdown Structure，工作分解结构）

| 用途 | 将项目工作分解为可管理的工作包 |
|------|-------------------------------|
| **原则** | 100% 原则 — 下一层之和 = 上一层 100% |
| **类型** | 交付物导向 / 阶段导向 / 功能导向 |
| **粒度** | 80 小时原则（每个工作包不超过 2 周） |

### 3.4 关键路径法（CPM, Critical Path Method）

| 提出 | 1950s，DuPont 公司 |
|------|-------------------|
| **用途** | 识别项目中最长（关键）路径，决定总工期 |
| **概念** | 浮动时间（Float）、关键任务、次关键路径 |

### 3.5 里程碑图（Milestone Chart）

简化的甘特图，只显示关键检查点。

### 3.6 燃尽/燃起图（Burn-down / Burn-up Chart）

| 用途 | 实时追踪 Sprint/Release 进度 |
|------|-----------------------------|
| **Burn-down** | 剩余工作量随时间下降 |
| **Burn-up** | 已完成工作量随时间上升 + 总范围线 |

**解读**：
- 实际线在理想线上方 → 落后进度
- 实际线在理想线下方 → 超前进度
- 总范围线上升（Burn-up）→ 范围蔓延

### 3.7 累积流图（CFD, Cumulative Flow Diagram）

| 用途 | 展示工作项在各阶段的累计分布 |
|------|-----------------------------|
| **解读**：各阶段之间的垂直距离 = 等待中的工作项数 |

## 4. 架构与设计工具

### 4.1 UML（Unified Modeling Language，统一建模语言）

| 提出 | 1997 年，Rational Software（Grady Booch, Ivar Jacobson, James Rumbaugh）|
|------|------------------------------------------------------------------------|
| **版本** | UML 2.5（最新） |
| **用途** | 标准化的软件系统可视化建模语言 |

**14 种图**（2 大类）：

**结构图（7 种）**：
| 图类型 | 用途 |
|--------|------|
| **类图**（Class Diagram） | 系统静态结构，类/接口/关系 |
| **对象图**（Object Diagram） | 特定时刻的实例快照 |
| **组件图**（Component Diagram） | 组件及其依赖和接口 |
| **部署图**（Deployment Diagram） | 物理硬件和软件部署 |
| **包图**（Package Diagram） | 命名空间和依赖 |
| **组合结构图** | 类内部的运行时组合 |
| **制品图** | 物理文件/制品 |

**行为图（7 种）**：
| 图类型 | 用途 |
|--------|------|
| **用例图**（Use Case Diagram） | 系统功能与参与者关系 |
| **活动图**（Activity Diagram） | 业务逻辑流程 |
| **状态机图**（State Machine Diagram） | 对象的状态转换 |
| **序列图**（Sequence Diagram） | 对象间消息交互的时间顺序 |
| **通信图**（Communication Diagram） | 对象间消息连接 |
| **时序图**（Timing Diagram） | 时间约束 |
| **交互概览图** | 组合序列图和活动图 |

### 4.2 C4 模型

| 提出 | Simon Brown（2011） |
|------|---------------------|
| **用途** | 轻量级软件架构可视化 |
| **核心理念** | 4 个抽象层次，从宏观到微观 |

**4 层**：

```
C1 - Context（系统上下文图）
    ├── 你的系统（中间的一个方块）
    ├── 用户角色
    ├── 外部依赖系统
    └── 适用于：技术/非技术听众

    ↓ zoom in

C2 - Container（容器图）
    ├── Web App、API 服务、数据库、消息队列
    ├── 每个容器：技术选型 + 职责
    └── 适用于：开发团队

    ↓ zoom in

C3 - Component（组件图）
    ├── 每个容器内部的模块/服务/控制器
    ├── 组件间接口和关系
    └── 适用于：架构师/开发者

    ↓ zoom in

C4 - Code（代码图）
    ├── UML 类图 / ERD 等细节
    ├── 按需创建，并非必须
    └── 适用于：具体实现参考
```

**表示方式**：方框 + 箭头 + 标签（不使用 UML 符号）

**工具支持**：Structurizr（DSL 驱动）、IcePanel、Visual C4、PlantUML

### 4.3 ADR（Architecture Decision Record，架构决策记录）

| 提出 | Michael Nygard（2011），*Documenting Architecture Decisions* |
|------|-------------------------------------------------------------|
| **用途** | 记录架构决策及其上下文和后果 |
| **经典模板**（Nygard 格式） | 标题：ADR-NNN: <决策标题> |

```
# ADR-001: 使用 PostgreSQL 作为主数据库

## Status
Accepted

## Context
需要选择一个关系型数据库。团队经验主要在 PostgreSQL 上。
数据一致性要求高。

## Decision
选用 PostgreSQL 15。

## Consequences
- 利用 PostgreSQL 的 JSON 类型，可以减少一些 NoSQL 需求
- 需要设置流复制以实现高可用
- 团队不需要额外学习

## Alternatives Considered
- MySQL：ORM 兼容性好，但 JSON 支持较弱
- CockroachDB：水平扩展更强，但运维复杂度高
```

**其他常用模板**：
- **Y-Statements**：`In the context of <situation>, facing <concern>, we decided for <option> to achieve <quality>, accepting <downside>`
- **MADR（Markdown ADR）**：Markdown 格式的 ADR 标准

### 4.4 ERD（Entity-Relationship Diagram，实体关系图）

| 提出 | Peter Chen（1976） |
|------|-------------------|
| **用途** | 数据建模，显示实体和关系 |
| **要素** | 实体（矩形）、属性（椭圆）、关系（菱形） |

### 4.5 DFD（Data Flow Diagram，数据流图）

| 用途 | 显示数据的输入、处理、存储和输出 |
|------|--------------------------------|
| **级别** | Level 0（上下文图）、Level 1、Level 2... |
| **要素** | 外部实体、过程、数据存储、数据流 |

### 4.6 状态图（State Diagram / State Machine）

| 用途 | 有限状态机的可视化 |
|------|-------------------|
| **要素** | 状态、转换、事件、动作 |
| **软件用例** | 订单状态、工作流引擎、UI 状态管理 |

## 5. 敏捷估算工具

### 5.1 Planning Poker（扑克估算）

| 提出 | 2002，James Grenning；后由 Mike Cohn 推广 |
|------|------------------------------------------|
| **用途** | 团队协作估算 User Story 的大小（Story Points） |
| **牌值** | 斐波那契数列：0, 1, 2, 3, 5, 8, 13, 20, 40, 100, ∞, ? |

**流程**：
1. PO 讲解一个 Story
2. 每人打出一张牌（同时亮牌）
3. 如果差异大 → 高低方各自说明理由
4. 重新出牌，直到趋同

### 5.2 T-Shirt Sizing（T 恤尺码估算）

| 尺码 | 含义 | 近似 Story Points |
|------|------|------------------|
| XS | 极小（1-2 小时） | 1 |
| S | 小（半天） | 2-3 |
| M | 中（1-2 天） | 5 |
| L | 大（3-5 天） | 8-13 |
| XL | 超大（1-2 周） | 20+ |
| XXL | 极大（> 2 周） | 需要拆解 |

### 5.3 Affinity Mapping（亲和图估算）

| 用途 | 快速对大量 Story 进行相对估算 |
|------|-----------------------------|
| **流程** | 将 Story 写在卡片上 → 团队成员静默排列 → 讨论调整 → 标记尺码 |

### 5.4 Bucket System（桶系统）

| 用途 | 快速估算大量项目，不用逐一讨论 |
|------|-----------------------------|
| **流程** | 设定 8-10 个"桶"（0, 1, 2, 4, 8, 16...）→ 每个项目放入一个桶 |

### 5.5 Dot Voting（点投票）

| 用途 | 优先级排序而非估算 |
|------|------------------|
| **流程** | 每人 N 个"点"→ 贴在优先考虑的项目上 |

### 5.6 Story Points vs Ideal Days

| 维度 | Story Points | Ideal Days |
|------|-------------|------------|
| 含义 | 相对复杂度 | 理想人天 |
| 随时间变化 | 不变（参照物固定） | 变（团队速度变化） |
| 沟通 | 抽象，需解释 | 直观 |
| 外界压力 | 不易施加 | 容易被挑战 |

### 5.7 Affinity Estimation（关联估算）

结合 Affinity Mapping + T-Shirt Sizing，适用于 backlog 很大时的快速估算。

## 6. 回顾技术

### 6.1 Start / Stop / Continue

| 用途 | 最简单的回顾格式 |
|------|-----------------|
| **格式** | 三个栏：Start（开始做）/ Stop（停止做）/ Continue（继续做） |

### 6.2 Starfish（海星回顾）

| 用途 | Start/Stop/Continue 的扩展版 |
|------|-----------------------------|
| **5 栏** | Start（开始）/ Stop（停止）/ Continue（继续）/ More of（多做）/ Less of（少做） |

### 6.3 Mad / Sad / Glad

| 用途 | 从情绪出发 |
|------|-----------|
| **Mad**（生气）— 流程问题、外部障碍 |
| **Sad**（失望）— 产品决策、遗漏的功能 |
| **Glad**（开心）— 成就、协作、个人成长 |

### 6.4 4Ls

| L | 含义 |
|---|------|
| **Liked**（喜欢） | 做得好，应该继续保持 |
| **Learned**（学到） | 学到了什么新东西 |
| **Lacked**（缺乏） | 缺少什么 |
| **Longed For**（渴望） | 希望未来有什么 |

### 6.5 Sailboat（帆船回顾）

**隐喻**：
- **船** — 团队
- **岛** — 目标
- **风** — 推动前进的积极因素
- **锚** — 拖慢进度的阻碍
- **暗礁** — 潜在风险

### 6.6 Timeline（时间线回顾）

按时间顺序列出 Sprint 中的所有事件 → 讨论情绪高低点 → 提取洞见

### 6.7 4F（Facts, Feelings, Findings, Future）

| 阶段 | 内容 |
|------|------|
| Facts | 发生了什么事实 |
| Feelings | 感受如何 |
| Findings | 学到了什么 |
| Future | 未来怎么做 |

### 6.8 Rose, Thorn, Bud

| 类型 | 含义 |
|------|------|
| **Rose** | 值得庆祝的成就 |
| **Thorn** | 不顺心的事 |
| **Bud** | 有潜力的新想法 |

## 7. 沟通与责任矩阵工具

### 7.1 RACI 矩阵

| 提出 | 1950s |
|------|------|
| **用途** | 明确角色和职责 |
| **全称** | Responsible（执行者）, Accountable（负责人）, Consulted（咨询）, Informed（告知） |

**示例**：

| 任务 | PM | Developer | QA | Design |
|------|----|-----------|-----|--------|
| 需求定义 | **A** | **R** | C | C |
| 代码实现 | I | **A**/**R** | I | C |
| 测试 | I | C | **A**/**R** | I |
| 上线 | **A** | **R** | I | I |

**常见问题**: 多个 A 或没有 A → 职责不清

**变体**：
- **RASCI**：+ Support（支持者）
- **DACI**：Driver（驱动者）, Approver（审批者）, Contributors（贡献者）, Informed（被告知）
- **RAPID**（Bain）：Recommend（建议）, Agree（同意）, Perform（执行）, Input（输入）, Decide（决定）

### 7.2 Communication Plan（沟通计划）

| 要素 | 内容 |
|------|------|
| 利益相关者 | 谁需要什么信息 |
| 信息 | 什么内容 |
| 频率 | 多久一次 |
| 渠道 | 邮件、Slack、会议、Jira |
| 格式 | 报告、Dashboard、演示 |

### 7.3 Stakeholder Matrix（利益相关者矩阵）

| 权力/利益 | 低利益 | 高利益 |
|-----------|--------|--------|
| **高权力** | 保持满意 | 重点管理 |
| **低权力** | 最小关注 | 保持被告知 |

## 8. 流程分析与改进工具

### 8.1 价值流图（VSM, Value Stream Mapping）

| 起源 | Lean Manufacturing |
|------|-------------------|
| **用途** | 分析端到端的流程，识别浪费 |

**要素**：信息流 + 物料流 + 时间线（增值时间 / 非增值时间）

**软件应用**：从需求提出到上线的时间分析

### 8.2 SIPOC 图

| 用途 | 高层次流程分析 |
|------|--------------|
| **全称** | Suppliers（供应者）, Inputs（输入）, Process（过程）, Outputs（输出）, Customers（客户） |

### 8.3 Value Chain（价值链分析）

| 提出 | Michael Porter（1985） |
|------|-----------------------|
| **用途** | 分析组织如何创造价值 |

**主要活动**：进货后勤 → 运营 → 出货后勤 → 营销 → 服务
**支持活动**：采购、技术开发、人力资源、基础设施

### 8.4 Business Model Canvas（商业模式画布）

| 提出 | Alex Osterwalder（2005） |
|------|-------------------------|
| **9 格** | 客户细分、价值主张、渠道、客户关系、收入来源 |
| | 关键资源、关键活动、关键伙伴、成本结构 |

### 8.5 流程图（Flowchart）

| 用途 | 可视化算法、业务流程、决策逻辑 |
|------|-------------------------------|
| **常用符号** | 开始/结束（圆角矩形）、过程（矩形）、决策（菱形）、文档（卷角矩形） |

## 9. 需求与用户故事工具

### 9.1 User Story Mapping（用户故事地图）

| 提出 | Jeff Patton（2014） |
|------|-------------------|
| **用途** | 在二维平面上组织用户故事：横轴为用户活动顺序，纵轴为优先级 |

**结构**：
```
                用户活动（横轴：时间顺序）
                ┌─────┬─────┬─────┬─────┐
      MVP 线     │     │     │     │     │  ← 第一版
      ──────────┼─────┼─────┼─────┼─────┤
      V2        │     │     │     │     │  ← 后续版本
                └─────┴─────┴─────┴─────┘
                  用户故事（纵轴：优先级）
```

### 9.2 User Story（用户故事）+ INVEST 原则

**标准格式**：
```
As a <角色>,
I want <功能>,
So that <价值>.
```

**INVEST**：
- **I**ndependent（独立）
- **N**egotiable（可协商）
- **V**aluable（有价值）
- **E**stimatable（可估算）
- **S**mall（足够小）
- **T**estable（可测试）

### 9.3 Acceptance Criteria（验收标准）

**Given/When/Then 格式**（来自 BDD）：
```
Given 用户已登录
When  用户点击"发布"按钮
Then  文章状态变为"已发布"
And   通知被发送给所有订阅者
```

### 9.4 Persona（用户画像）

| 用途 | 创建真实的用户代表角色，指导设计决策 |
|------|-----------------------------------|
| 要素 | 姓名、年龄、职业、目标、痛点、技术熟练度 |

### 9.5 Impact Mapping（影响地图）

| 提出 | Gojko Adzic（2012） |
|------|-------------------|
| **用途** | 将业务目标与功能需求链接 |
| **结构** | Why（目标）→ Who（角色）→ How（影响）→ What（功能） |

## 10. 风险管理工具

### 10.1 风险登记册（Risk Register）

| 要素 | 内容 |
|------|------|
| 风险描述 | 如果...可能... |
| 概率 | 高/中/低 |
| 影响 | 高/中/低 |
| 风险评分 | 概率 × 影响 |
| 应对策略 | 规避/转移/减轻/接受 |
| 负责人 | 谁跟踪 |

### 10.2 SWOT 分析

| 提出 | Albert Humphrey（1960s） |
|------|-------------------------|
| **用途** | 内外部环境分析 |
| **四象** | Strengths（优势）/ Weaknesses（劣势）/ Opportunities（机会）/ Threats（威胁） |

### 10.3 PESTEL 分析

| 用途 | 宏观环境分析 |
|------|-------------|
| **要素** | Political（政治）、Economic（经济）、Social（社会）、Technological（技术）、Environmental（环境）、Legal（法律） |

### 10.4 FMEA（Failure Mode and Effects Analysis，失效模式与影响分析）

| 提出 | 1940s，美国军方 |
|------|---------------|
| **用途** | 预防性识别潜在的失效模式及其影响 |
| **RPN 评分** | Severity（严重度）× Occurrence（发生度）× Detection（检测度） |

### 10.5 风险矩阵（Risk Matrix / Heat Map）

| 用途 | 可视化风险等级 |
|------|--------------|
| **轴** | 概率 × 影响 |
| **区域** | 低（绿）/中（黄）/高（红）/极高（深红） |

## 11. 决策工具

### 11.1 决策矩阵（Decision Matrix / Pugh Matrix）

| 用途 | 在多方案中系统化选择 |
|------|-------------------|
| **方法** | 设定权重 → 每个方案打分 → 计算加权总分 |

### 11.2 力场分析（Force Field Analysis）

| 提出 | Kurt Lewin（1940s） |
|------|-------------------|
| **用途** | 分析变革的驱动力和阻力 |
| **结构** | 驱动力 ← [当前状态] → 阻力 |

### 11.3 MoSCoW 优先级排序

| 提出 | Dai Clegg，Oracle |
|------|-----------------|
| **用途** | 需求优先级排序 |
| **全称** | Must have / Should have / Could have / Won't have |

### 11.4 Kano Model（狩野模型）

| 提出 | Noriaki Kano（1984） |
|------|-------------------|
| **用途** | 分类功能特性对用户满意度的影响 |

| 类别 | 说明 |
|------|------|
| **基本型（Must-be）** | 没有会不满，有不会更满意 |
| **期望型（One-dimensional）** | 越多越满意 |
| **兴奋型（Attractive）** | 没有没关系，有会惊喜 |
| **无差异型（Indifferent）** | 有没有都一样 |
| **反向型（Reverse）** | 有反而会不满 |

### 11.5 Eisenhower Matrix（艾森豪威尔矩阵）/ 四象限法

| 紧急/重要 | 不紧急 |
|-----------|--------|
| **重要** | Do First（先做） | Schedule（计划做） |
| **不重要** | Delegate（授权） | Eliminate（不做） |

## A. 工具选择速查表

| 你遇到的问题是 | 用什么工具 |
|--------------|----------|
| 系统出问题了，不知道原因 | **鱼骨图** + **5 Whys** |
| 质量不稳定，想持续监控 | **控制图** + **直方图** |
| 缺陷太多了，不知道先修什么 | **帕累托图**（80/20） |
| 项目范围太大了，没法管理 | **WBS** 分解 |
| 需要向团队展示项目进度 | **甘特图** / **燃尽图** |
| 需要向非技术人员展示架构 | **C4 Context 图** |
| 需要记录一个技术决策 | **ADR** |
| 需要估算 Story 的工作量 | **Planning Poker** / **T-Shirt Sizing** |
| Sprint 结束了，想回顾改进 | **Start/Stop/Continue** / **Mad/Sad/Glad** |
| 任务和职责不清楚 | **RACI 矩阵** |
| 需求要排序 | **MoSCoW** / **Kano Model** |
| 需要分析外部风险 | **SWOT** / **PESTEL** |
| 流程太慢，想找出浪费 | **价值流图（VSM）** |
| 用户需求说不清楚 | **User Story Mapping** |
| 不知道哪个方案最优 | **决策矩阵** |
| AI 代理不遵循流程 | **Superpowers 压力场景测试** |
| 需要跨模型验证代码 | **gstack /codex** |
