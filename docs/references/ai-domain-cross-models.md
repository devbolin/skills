# AI 领域可应用的跨域思维模型与方法论

## 说明

本文档收集来自认知心理学、行为经济学、系统科学、军事策略、教育学等领域的思维模型和框架，分析它们如何在 AI Agent 和技能（Skill）设计中发挥作用。

---

## 1. 认知偏差（Cognitive Biases）—— 理解与利用 LLM 的决策偏误

### 背景

LLM 不仅在训练数据中吸收了人类的认知偏差，还会在推理过程中放大它们。这对于 Agent 技能设计有双重意义：
1. **需要防范**：Agent 可能因为认知偏差做出错误决策
2. **可以利用**：通过设计"选择架构"引导 Agent 做出正确决策

### 对 Agent 行为影响最大的偏差

| 偏差 | 定义 | 在 Agent 中的表现 | 技能设计中的应用 |
|------|------|------------------|-----------------|
| **锚定效应** | 第一印象或第一个数字强烈影响后续判断 | 第一个看到的方案会被作为基准 | 在技能中先给出正确的"锚" |
| **确认偏误** | 倾向于寻找支持已有观点的证据 | Agent 可能忽略与自己初始分析矛盾的证据 | 强制要求列出反方观点 |
| **可得性启发** | 更容易想起的事被认为更常见 | Agent 倾向于用训练数据中最常见的模式 | 在技能中定义精确的决策标准 |
| **框架效应** | 问题的呈现方式影响回答 | "80% 存活率" vs "20% 死亡率" 产生不同选择 | 使用正面框架引导正确行为 |
| **沉没成本** | 已经投入的不可回收成本影响决策 | "已经写了 45 分钟测试，虽然技能说另一种方式更好..." | Superpowers 的压力场景直接使用此偏差测试技能强度 |
| **现状偏差** | 倾向于维持当前状态 | Agent 会用熟悉的方案而不是最优方案 | 要求 Agent 评估至少 2 个替代方案 |
| **过度自信** | 对自己判断的自信超过实际准确率 | "我是认证专家，不需要查技能" | Superpowers 的压力场景 1 |
| **选择支持偏差** | 选择后倾向于高估选择对象的价值 | Agent 选择方案后会更坚持它 | 两阶段审查使用独立子代理 |
| **从众效应** | 跟随多数人的选择 | "大多数项目用微服务" | 在技能中用权威语气代替"流行" |
| **后见之明偏差** | 事件发生后认为结果是可以预测的 | "我早就知道这个方案不行" | 记录决策时的理由，避免事后偏见 |

### 在 Agent Skill 设计中的应用

```
策略 1: 利用"锚定效应"
  ┌─ 技能中先给出正确的选择框架
  └─ 示例：不要在技能中列 "方案 A/B/C 都可以"
         而是："按以下优先级评估：1) 安全性 2) 性能 3) 可维护性"

策略 2: 防止"确认偏误"
  ┌─ 要求 Agent 在做出决策前列出至少 2 个反方观点
  └─ 示例："在推荐任何方案前，列出它的三个潜在问题"

策略 3: 对抗"沉没成本"
  ┌─ Superpowers 的方法：在技能中明确阻止
  └─ 示例："即使你已经写了一些代码，如果它不符合 plan.md，必须重做"

策略 4: 利用"框架效应"
  ┌─ 正确的框架 = 正确的行为
  └─ 好："遵循此技能将确保代码质量达到标准"
         差："不遵循此技能可能导致代码质量问题"
```

### 学术引用

- *"Cognitive Bias in Decision-Making with LLMs"* (EMNLP 2024) — 13,465 个 prompt 测试 LLM 在 3 类偏差上的表现
- *"Call Me a Jerk: Persuading AI"* (Wharton, Cialdini 参与) — 证明说服原则对 LLM 有效
- *"Large language models show amplified cognitive biases in moral judgments"* (PNAS 2025)

## 2. 助推理论与选择架构（Nudge Theory & Choice Architecture）

### 背景

| 提出 | Richard Thaler（诺贝尔经济学奖 2017）& Cass Sunstein，2008《Nudge》 |
|------|----------------------------------------------------------------|
| 核心 | 通过设计"选择架构"（Choice Architecture）在不限制自由的前提下引导人们做出更好的选择 |
| 术语 | **自由意志式家长主义**（Libertarian Paternalism） |

### 六大助推原则

| 原则 | 定义 | AI Agent 技能中的对应 |
|------|------|---------------------|
| **默认选项**（Default） | 大多数人会接受默认设置 | 技能的"默认路径"应该是正确的路径 |
| **社会规范**（Social Norms） | 人们倾向于按社会规范行事 | `The agent checks for relevant skills before any task`（Superpowers）|
| **简化**（Simplify） | 减少选择复杂度和步骤 | 技能将复杂流程分解为清晰的步骤 |
| **反馈**（Feedback） | 即时反馈改善决策 | 两阶段审查的即时结果 |
| **预承诺**（Precommitment） | 提前承诺影响后续行为 | 要求 Agent 宣布正在使用的技能 |
| **损失厌恶**（Loss Aversion） | 损失的痛苦 > 收益的快乐 | "不遵循技能将导致审查阻塞" |

### 对 LLM Agent 的特殊性

与人类不同，LLM Agent 没有"自由意志"，但 Thaler 的理论仍然适用——因为 **Agent 的"默认行为"就是跳过流程直接写代码**。

```
助推的设计目标：
  从 Agent 的默认路径（捷径/跳过流程）
       ↓
  改变为     正确路径（遵循技能/逐步执行）

实现方式：
  └─ 改变"选择架构"— 不是增加选项，而是让正确路径成为最省力的路径
  └─ 示例：Superpowers 的 `1% 规则`
      └─ 不是 "鼓励检查技能"
      └─ 而是 "如果不检查技能，就不应该开始任务"
```

### 与 Cialdini 说服原则的区别

| 维度 | 助推（Nudge） | 说服（Persuasion） |
|------|-------------|-------------------|
| 机制 | 改变环境/选择架构 | 改变认知/态度 |
| 意识 | 通常无意识 | 可以有意识 |
| 伦理 | 保留自由选择 | 可能更具操纵性 |
| LLM 应用 | 改变 prompt 结构 | 使用权威/承诺/社会认同 |
| 示例 | 让技能加载成为默认 | "IMPORTANT: 这是强制性的" |

## 3. Cynefin 框架

### 背景

| 提出 | Dave Snowden，1999（IBM Global Services） |
|------|------------------------------------------|
| 名称来源 | 威尔士语，意为"栖息地" |
| 用途 | **意义建构**（Sensemaking）—— 将问题分类，以确定正确的应对策略 |

### 五个领域

```
                    ┌──────────────────────────┐
                    │         Disorder          │
                    │      （混乱/未知）          │
                    └──────────────────────────┘

  Clear（清晰）         │           Complicated（复杂但可分析）
  Cause → Effect        │           Cause ← Effect（需分析）
  所有人可见              │           需要专家判断
  Sense → Categorize → Respond  │  Sense → Analyze → Respond
  ┌─ 适合规则驱动        │           ┌─ 适合专家系统
  └─ 可以自动化          │           └─ 需要人类专家参与
                        │
  ──────────────────────┼──────────────────────────
                        │
  Complex（复杂不可预测） │          Chaotic（混沌）
  Cause ←→ Effect（事后可理解）│     Cause → ? → ?
  Probe → Sense → Respond  │  Act → Sense → Respond
  ┌─ 需要实验            │           ┌─ 需要立即行动
  └─ 适合 AI 探索        │           └─ 先稳定再分析
```

| 域 | 因果关系 | 策略 | 示例 |
|----|---------|------|------|
| **Clear**（清晰） | 因果明确 | 感知 → 分类 → 响应 | 已知 bug 修复、执行例行任务 |
| **Complicated**（复杂但可分析） | 需分析才能发现 | 感知 → 分析 → 响应 | 性能优化、系统设计 |
| **Complex**（复杂不可预测） | 只有事后才能理解 | 试错 → 感知 → 响应 | 新产品设计、架构演进 |
| **Chaotic**（混沌） | 无因果 | 行动 → 感知 → 响应 | 生产宕机、安全攻击 |
| **Disorder**（混乱） | 不知道在哪个域 | 先分解到四个域 | 不熟悉的新问题 |

### 在 AI Agent 和 Skill 设计中的应用

```
应用 1: Skill 分类

  Clear → 使用规则型 Skill（checklist、流程步骤）
           └─ 示例：code review checklist skill

  Complicated → 使用分析型 Skill（提供分析框架和数据源）
                 └─ 示例：performance debugging skill（需要分析堆栈、Profiling 数据）

  Complex → 使用实验型 Skill（提供实验框架和验证方法）
             └─ 示例：architectural decision skill（用 ADR 记录实验和决策）

  Chaotic → 使用行动型 Skill（立即行动 + 逐步稳定）
             └─ 示例：incident response skill（先止血 -> 再分析 -> 再修复）

应用 2: 决定 Automation vs Human-in-the-loop

  Clear → 可全自动执行（Agent 独立完成）
  Complicated → Agent 分析 + 人类审批
  Complex → Agent 提供方案 → 人类决策
  Chaotic → 人类主导 → Agent 执行

应用 3: Skill 自身的验证策略

  Clear −→ 用单元测试验证（输入 → 期望输出）
  Complicated −→ 用专家评审验证
  Complex −→ 用 A/B 测试验证
  Chaotic −→ 用复盘验证
```

## 4. OODA 循环

### 背景

| 提出 | Col. John Boyd（美国空军，1960s） |
|------|---------------------------------|
| 原始用途 | 战斗机空战格斗中的决策周期优化 |
| 核心 | **谁更快完成 OODA 循环，谁就赢得对抗** |

### 四阶段

```
Observe（观察）
  └─ 收集信息：环境、对手、状态

     ↓

Orient（定向）
  └─ 解释信息：用经验、知识、心理模型理解情况
  └─ 这是最关键的一步——Boyd 认为它决定一切

     ↓

Decide（决策）
  └─ 选择行动方案

     ↓

Act（行动）
  └─ 执行决策

     ↓
  (回到 Observe — 循环)
```

### "Orient" 的深意

Boyd 强调 **Orient 是所有阶段中最关键的**。它取决于：

```
遗传 + 文化传统 + 先验知识 + 新信息 → 形成心智模型（Mental Model）

如果心智模型是错误的 → 后续 Observe/Decide/Act 全部错误
```

### 在 AI Agent 设计中的应用

#### 应用 1：Agent 工作循环

这是现代 AI Agent 架构的核心模式：

```
LLM Agent 的 OODA 循环：

Observe（观察）
  └─ 读取用户输入
  └─ 读取项目上下文（AGENTS.md）
  └─ 加载相关技能（SKILL.md）

Orient（定向）
  └─ 理解任务类型
  └─ 匹配最合适的技能
  └─ 构建心智模型："这是一个代码审查任务"

Decide（决策）
  └─ "我将遵循 code-review 技能"

Act（行动）
  └─ 执行 code review
  └─ 输出结果
```

#### 应用 2：OODA 速度

Boyd 认为 OODA 循环的速度比精度更重要。在 AI 领域：

```
错误对比：
  慢 OODA: Agent 读 3 个技能后困惑 → 用户纠正 → 重读 → 最终做对了但花了 20 分钟
  快 OODA: Agent 先读最匹配的技能 → 做 → 用户反馈 → 调整 → 10 分钟完成

  关键不是"一次做对"，而是"快速迭代"
```

#### 应用 3：子代理的 OODA

```
Superpowers 的子代理策略本质上是加速 OODA：
  └─ 每个子代理从零开始 Observe（只接收 context）
  └─ Orient 更清晰（任务范围窄）
  └─ Decide 更快（不需要考虑其他任务）
  └─ Act 专一（只做一件事）

对比：单个代理处理所有任务 → Orient 阶段被 5 个任务的心智模型污染
```

#### 应用 4：与 Cynefin 结合

```
Clear → 短的 OODA（直接 Observe → Categorize → Respond）
Complicated → 加长的 OODA（需要更多 Orient 阶段的分析）
Complex → 迭代 OODA（多次实验 → 观察 → 调整）
Chaotic → 压缩 OODA（先 Act 来稳定局势）
```

## 5. 约束理论（Theory of Constraints, TOC）

### 背景

| 提出 | Eliyahu Goldratt，1984《The Goal》 |
|------|-----------------------------------|
| 核心 | 任何系统都存在至少一个约束（瓶颈），系统的整体产出由这个瓶颈决定 |
| 类比 | 一条链的强度取决于最弱的链环 |

### 五步聚焦法（Five Focusing Steps）

```
Step 1: 识别约束（Identify）
  └─ 找到系统中限制整体 throughput 的因素

Step 2: 利用约束（Exploit）
  └─ 在不增加投入的前提下最大化约束的产出

Step 3: 服从约束（Subordinate）
  └─ 系统的其他部分配合约束的节奏

Step 4: 提升约束（Elevate）
  └─ 增加投入以消除约束

Step 5: 重复（Repeat）
  └─ 约束被打破 → 出现新约束 → 回到 Step 1
```

### 在软件开发和 AI Agent 中的应用

#### 应用 1：识别 Agent 流程中的瓶颈

```
传统软件开发流程的瓶颈：
  └─ 需求分析（慢）→ 阻塞 编码（快）→ 阻塞 测试（最慢）

AI Agent 时代，瓶颈发生了变化：
  └─ 代码生成（极快）→ 代码审查（快）→ 需求定义（慢）→ 架构决策（最慢）

  Goldratt 的洞见：当 AI 加速了一环，瓶颈会向上游或下游移动

  "The bottleneck has moved" — Jim Grey, 2026
```

#### 应用 2：Agent 工作流的 TOC

```
Step 1: 识别约束
  └─ Agent 会话中，哪个步骤最慢？
      常见：上下文窗口满（"忘记"之前的决策）

Step 2: 利用约束
  └─ 最大化上下文窗口的利用效率
      做法：用渐进式披露按需加载，不让无关信息占据上下文

Step 3: 服从约束
  └─ 所有步骤配合上下文管理的节奏
      做法：每个子代理只接收最小的必要上下文

Step 4: 提升约束
  └─ 增加上下文窗口（技术升级时）
      或采用子代理隔离（不需要大窗口，需要正确的窗口）

Step 5: 重复
  └─ 上下文不再是瓶颈 → review 是瓶颈 → 用两阶段审查优化
```

#### 应用 3：Skill 设计的 TOC

```
用户在 Agent 中的瓶颈通常不是写代码
而是：Agent 跳过流程、Agent 忘记上下文、Agent 不理解需求

设计技能时直接针对这些瓶颈：
  ├── 跳过流程 ← 说服原理
  ├── 忘记上下文 ← 渐进式披露 + 文件持久化
  └── 不理解需求 ← brainstorming + plan.md
```

## 6. 德雷福斯技能获取模型（Dreyfus Model of Skill Acquisition）

### 背景

| 提出 | Hubert & Stuart Dreyfus，1980，为美国空军研究飞行员技能习得 |
|------|-----------------------------------------------------------|
| 核心 | 技能习得经历从依赖规则到依赖直觉的五个阶段 |

### 五个阶段

| 阶段 | 特征 | 决策方式 | 规则依赖 |
|------|------|---------|---------|
| **Novice（新手）** | 需要明确的规则和步骤 | 按规则一步一步做 | 高 |
| **Advanced Beginner（高级新手）** | 需要真实场景和经验 | 开始识别模式，但还不能区分优先级 | 中高 |
| **Competent（胜任者）** | 能制定计划，解决问题 | 有意识地选择和决策 | 中 |
| **Proficient（精通者）** | 整体把握，能够自我纠正 | 直觉为主，分析为辅 | 低 |
| **Expert（专家）** | 完全直觉，知道但不一定说清为什么 | 直觉决策 | 极低 |

### 与 AI Agent 的映射

```
这个模型对 Agent Skill 设计有深刻的启示：

Agent 在"生来就是专家"和"实际上像新手"之间摇摆：

  └─ 训练数据层面：Agent 见过几百万个代码库 → "像专家"
  └─ 执行任务层面：Agent 没有上下文，不知道项目惯例 → "像新手"

这就解释了为什么 Agent 需要技能：

  Skill 的作用 = 把 Agent 从 "假装专家" 拉回到 "结构化新手"
    因为新手阶段依赖规则和步骤
    而规则和步骤正是 SKILL.md 提供的东西
```

### 技能设计的阶段适配

```
Novice 阶段 → 技能应该是高结构化的
  └─ 清晰的命令式步骤
  └─ Check the list 格式
  └─ 不要"根据你的判断"，要说"先做 A，再做 B"

Advanced Beginner → 技能应该提供模式和反模式
  └─ "如果你看到 X，做 Y"
  └─ 包含常见陷阱

Competent → 技能应该提供决策框架
  └─ "用这个评估矩阵做决定"
  └─ 包含优先级规则

Proficient/Expert → 技能应该做参考
  └─ 只有触发条件和关键原则
  └─ 信任 Agent 的判断（在它有足够上下文时）

但现实是：Agent 始终是 "新手"（对每个新项目）。
所以大部分技能应该设计为 Novice 级别的指令。
```

### 对 Superpowers 设计的解释

```
Jesse Vincent 的目标：
  "Implementation plan clear enough for an enthusiastic junior engineer
   with poor taste, no judgement, no project context, and an aversion
   to testing to follow."

  这明确将目标定在 Dreyfus 模型的 Novice ~ Advanced Beginner 阶段。
  这意味着计划必须是：
  1. 结构化的（步骤清晰）
  2. 具体的（文件路径、代码范围）
  3. 可验证的（"Done when" 条件）
  4. 没有歧义的（不需要"判断"）
```

## 7. 心智模型栅格（Latticework of Mental Models）

### 背景

| 提出 | Charlie Munger，1994（南加州大学商学院演讲） |
|------|---------------------------------------------|
| 核心 | 单学科视角不足以解决复杂问题。需要从数学、物理、生物、心理学、经济学等不同学科借用心智模型 |
| 名言 | "对于一个只有锤子的人来说，所有问题看起来都像钉子。" |

### 已覆盖的跨学科模型

之前文档已覆盖 15 个经典模型。以下补充更多适用于 AI Agent 设计但尚未覆盖的：

| 模型 | 来源学科 | 适用于 AI 设计 | LLM Agent 行为映射 |
|------|---------|--------------|-------------------|
| **反馈回路**（Feedback Loop） | 系统动力学 | Agent 的自我纠错机制 | 执行 → 观察结果 → 调整 → 再执行 |
| **熵增定律** | 热力学/信息论 | 软件系统自然趋向混乱 | Agent 输出随着会话延长质量下降 |
| **复利效应** | 经济学 | 小改进的长期收益 | 每天改进 1% 的技能 → 一年强大 37 倍 |
| **回归均值** | 统计学 | 极端事件后的自然回复 | 不要因为一次失败的 Agent 对话就重做整个系统 |
| **选择性注意**（Cocktail Party Effect） | 心理学 | Agent 在大量信息中找到相关内容 | 注意力稀释问题 |
| **机会成本** | 经济学 | 选择一项技术 = 放弃其他 | 选择 Agent 框架的取舍 |
| **边际效益递减** | 经济学 | 80% 之后每 1% 的代价 | 从 80% → 90% 技能覆盖率的巨大成本 |
| **帕金森琐碎化**（Bikeshedding） | 管理 | 团队过度讨论小问题 | Agent 花大量 token 在次要问题上 |
| **安全边际**（Margin of Safety） | 工程/金融 | 超出需求的设计预留 | Agent 实现中的错误处理、降级策略 |
| **奥威尔式双重思想** | 文学 | 同时持有两个矛盾信念 | Agent 同时说"我遵循了 TDD"和"我没有写测试" |
| **汉隆剃刀** | 哲学 | 先假设失误而非恶意 | Agent 行为异常时，先怀疑技能设计而不是"Agent 不听话" |
| **斯特金定律** | 科幻 | 任何事物的 90% 都是垃圾 | 90% 的 Agent 输出需要被过滤/审查 |
| **格林定律**（Greene's Law） | 编程 | 任何足够复杂的系统... | Agent 系统的复杂度增长需要主动管理 |
| **霍夫施塔特定律** | 认知科学 | 完成时间总是比预期的长 | 即使是 Agent，"再迭代一次"也总比想象的长 |

## 8. 单双环学习（Single & Double Loop Learning）

### 背景

| 提出 | Chris Argyris & Donald Schön，1970s |
|------|------------------------------------|
| 核心 | 组织学习的两个层次：纠错（单环）vs 重建规则（双环） |

### 模型

```
单环学习（Single-Loop Learning）：
  目标 → 策略 → 结果 → 是否达成？→ 调整策略 → 再试
  └─ 在现有框架内改进
  └─ "我们做得怎么样？"

双环学习（Double-Loop Learning）：
  目标 → 策略 → 结果 → 是否达成？→ 质疑目标和假设 → 重建框架
  └─ 质疑和改变框架本身
  └─ "我们在做正确的事吗？"

三环学习（Triple-Loop Learning）：
  质疑：我们如何定义"在做什么"？我们是谁？
  └─ 改变学习本身的方式
```

### 在 AI Agent 中的应用

```
单环：
  Agent 输出结果 → 测试失败 → Agent 调整代码 → 测试通过
  └─ 这是日常的 TDD 循环

双环：
  Agent 输出结果 → 审查发现偏离 plan → 团队质疑 plan 本身
  └─ 这是两阶段审查的真正价值——不仅检查"做对了吗"，
     也审视"这个计划对吗"

三环：
  团队质疑：我们的 review 流程本身是否需要改变？
  这是 BMAD 的 Retro 环节 — 不是审视项目，是审视流程
```

### 在 Skill 设计中的应用

```
好的技能不仅教会 Agent 单环（如何做）
也教会 Agent 双环（何时质疑当前做法）

示例：code review skill
  单环部分：
  1. 检查变量命名
  2. 检查日志级别
  3. 检查错误处理

  双环部分：
  4. 如果这些检查花费超过 30 分钟
      → 考虑将这个模块拆分出去
      → 考虑是否有更好的设计模式
```

## 9. 事前验尸（Pre-Mortem）

### 背景

| 提出 | Gary Klein，2007 |
|------|-----------------|
| 核心 | 在项目开始前假设项目**已经失败**，然后回溯原因 |

### 与传统事后分析的对比

```
事后分析（Post-Mortem）：
  ── "项目失败了，来分析原因。"
  ── 问题：知道结果后，客观性受后见之明偏差影响

事前验尸（Pre-Mortem）：
  ── "假设项目在 6 个月后失败了。原因是什么？"
  ── 优势：没有后见之明偏差，团队敢于提出担心
```

### 在 AI Agent 设计中的应用

```
应用 1: 在新 Agent 工作流上线前

  "假设 3 个月后这个 Agent Skill 被弃用了。可能的原因是什么？"
  └─ Agent 总是跳过技能
  └─ 技能说明太模糊
  └─ 技能覆盖了错误的问题域
  └─ Token 成本太高

  事先识别这些风险 → 提前设计对策

应用 2: 在复杂功能的实现前

  plan.md 中嵌入事前验尸部分：
  "假设这个功能上线后失败了，最可能的原因会是：
  1. 我们忽略了哪种边界情况？
  2. 什么性能问题会导致问题？
  3. 用户最可能在什么地方感到困惑？"
```

## 10. MECE 原则（Mutually Exclusive, Collectively Exhaustive）

### 背景

| 提出 | Barbara Minto，《金字塔原理》（McKinsey）|
|------|----------------------------------------|
| 核心 | **相互独立，完全穷尽** — 分类的两个标准 |

### 定义

```
MECE 分类：
  └─ 子类之间不重叠（相互独立）
  └─ 子类合起来覆盖父类（完全穷尽）

非 MECE 示例（分类的常见错误）：
  └─ "前端 bug" 和 "样式 bug" — 重叠（样式在前端中）
  └─ "紧急" 和 "重要" — 不互斥（一个 bug 可以既紧急又重要）

MECE 示例：
  └─ 按浏览器：Chrome / Safari / Firefox / Others → 互斥且穷尽
  └─ 按严重等级：Critical / Major / Minor / Suggestion → 互斥且穷尽
```

### 在 AI Agent 和 Skill 设计中的应用

```
应用 1: Skill 描述中的分类

  好的分类：
    "Use for: code review, security audit, performance review"
    → 互斥且穷尽三种审查类型

  不好的分类：
    "Use for: code review, PR review, code quality check"
    → 重叠（code review = PR review = 一半的 code quality check）

应用 2: Skill 触发条件

  当 Agent 需要决定用哪个技能时，MECE 的触发条件可以帮助它做精确判断。

  技能 A：适用条件 = "代码已写完，未提交"
  技能 B：适用条件 = "代码已提交，PR 已创建"
  技能 C：适用条件 = "代码已合并到主分支"

  → 每个 PR 流程阶段都只对应一个技能（MECE）

应用 3: 错误分类

  两阶段审查的严重级别：
  Critical / Major / Minor / Suggestion
  → MECE 吗？是。每个问题只属于一个级别（互斥），覆盖所有可能性（穷尽）
```

## 11. 信号与噪声（Signal vs Noise）

### 背景

| 提出 | 概率论/统计学 → Nate Silver《信号与噪声》（2012） |
|------|------------------------------------------------|
| 核心 | 在大量数据中识别真正的信号，过滤随机噪声 |

### 在 AI Agent 设计中的应用

```
应用 1: 上下文窗口管理

  所有信息 = Signal + Noise
  Agent 的上下文窗口有限  → 目标：最大化 Signal/Noise 比

  渐进式披露 = Signal 优先的加载策略
  └─ Discovery 阶段：只加载 name + description（Signal 密度最高）
  └─ Loading 阶段：加载完整指令（Signal + 部分 Noise）
  └─ Deep Loading：加载脚本/模板（Signal 较低，按需）

应用 2: 两阶段审查

  第一阶段（Spec Compliance）的信号 = 功能偏离
  第二阶段（Code Quality）的信号 = 代码问题

  将两者分开 = 避免信号互相干扰（在第一阶段看不到代码时，更专注功能）

应用 3: 历史对话管理

  对话历史中，大量内容是 Noise（问候、确认、重复）
  只有关键的决策点是 Signal

  "记忆技能"的价值 = 从噪声中提取信号
  └─ 保存关键决策而非全部对话
```

## 12. 安全 I 与安全 II（Safety-I & Safety-II）

### 背景

| 提出 | Erik Hollnagel，2014《Safety-I and Safety-II》|
|------|---------------------------------------------|
| 核心 | 从"找错"转向"确保正确的事发生" |

### 对比

| 维度 | Safety-I | Safety-II |
|------|---------|----------|
| 定义 | 安全 = 不出错 | 安全 = 确保正确的事发生 |
| 方法 | 找根因、防复发 | 理解为什么大部分时间是对的，强化它 |
| 焦点 | 失败案例 | 成功案例 + 失败案例 |
| 假设 | 系统分解后可以分析 | 系统是复杂的、涌现的 |
| 人类角色 | 主要错误来源 | 主要适应性来源 |

### 在 AI Agent 中的应用

```
Safety-I 方法（当前主流）：
  └─ 当 Agent 出错时 → 分析根因 → 增加规则 → 防复发
  └─ 问题：规则越来越多，系统越来越复杂，规则之间开始矛盾

Safety-II 方法：
  └─ 理解 Agent 在什么情况下做对了 → 强化这些条件
  └─ 示例：不是"增加更多约束"，而是"改善 Agent 成功时的环境"

在 Skill 设计中的具体实践：

  Safety-I 示例：
    "Agent 跳过 TDD → 在技能中增加：'必须先写测试，否则不能写代码'"

  Safety-II 示例：
    "Agent 遵循 TDD 时，是什么条件让它成功了？
    → 任务小 → 计划清晰 → 有明确的 RED 步骤
    → 强化这些条件：确保每个任务都足够小、plan.md 足够清晰"
```
