## 1. 第一性原理

### 起源

| 人物 | 贡献 |
|------|------|
| **亚里士多德**（公元前 350） | 首次提出："在每个系统中都存在第一性原理，是最基本的命题，不能被违反。" |
| **笛卡尔**（1637） | 方法论怀疑——系统性地怀疑一切，直到找到不可怀疑的基础 |
| **理查德·费曼**（1960s） | 费曼技巧——将一个概念分解到最基础的部分来验证理解 |
| **埃隆·马斯克**（2002至今） | 最著名的现代实践者——用第一性原理重构了火箭、电动车、隧道等行业 |

### 定义

**第一性原理**是指将问题分解为其最基本的真理或假设，然后从这些基础出发向上推理，而不是通过类比或现有方案来思考。

### 类比思维 vs 第一性原理

```
类比思维（Analogy Thinking）：
  "别人的火箭成本是 6500 万美元，
   所以我们也应该差不多这个价。"

第一性原理（First Principles）：
  "火箭由什么制成？航空级铝合金 + 钛 + 铜。
   这些材料在市场上的成本是多少？
   大约是原材料成本的 2%。剩下的 98% 去哪了？"
```

马斯克得出的结论：原材料成本只有传统火箭价格的 2%，其余是制造效率、供应链复杂度和垄断利润。SpaceX 通过垂直整合把发射成本降到传统方式的 1/10。

### 四步法

```
Step 1: 识别并定义问题
  └─ 你真正想解决的是什么？不是表面症状。

Step 2: 分解到基本要素
  └─ 不断追问"这由什么构成？"直到不可再分。
  └─ 区分：哪些是基本事实？哪些是假设/惯例？

Step 3: 挑战假设
  └─ "这件事必须这样做吗？还是因为一直都这么做？"
  └─ 三个假设层：
       ├─ 市场假设（市场本来就是这样）
       ├─ 问题假设（问题只能这样解决）
       └─ 解决方案假设（只能用这个方案）

Step 4: 从零重建
  └─ 基于基本事实，而不是基于现有方案，重新设计。
```

### 在软件开发中的应用

#### 示例 1：系统设计决策

```
问题：微服务太复杂了，要不要用？

类比思维：大家都在用微服务，我们也用。

第一性原理：
  分解：
  └─ 我们需要什么？——独立部署、团队自治、故障隔离
  └─ 核心需求是什么？——不是"微服务"，而是"独立变化能力"
  └─ 最小方案是什么？
       ├─ 模块化单体（Modular Monolith）可能就够了
       ├─ 独立部署可以通过 Feature Flag + CI/CD 实现
       └─ 故障隔离可以通过进程边界或容器实现
```

#### 示例 2：测试策略

```
问题：测试覆盖率不够。

类比思维：行业标准是 80%，我们也要 80%。

第一性原理：
  分解：
  └─ 测试解决了什么问题？——防止回归、验证行为、文档化预期
  └─ 覆盖率是手段还是目的？——目的是信心，不是百分比
  └─ 如何以最小代价建立信心？
       ├─ 核心业务逻辑需要精确的单元测试
       ├─ 集成路径需要契约测试
       └─ UI 变化频繁，少量 E2E 即可
```

#### 示例 3：数据库选型

```
类比思维：创业公司都用 PostgreSQL，所以我们也用。

第一性原理：
  └─ 我们的数据模型是什么？——关系型还是文档型？
  └─ 查询模式是什么？——大量读、大量写、还是分析型？
  └─ 一致性要求多高？——强一致还是最终一致？
  └─ 团队熟悉什么？——维护成本也是真实成本
```

### 在 Agent Skill 设计中的应用

```
问题：为什么 Agent 不遵循 TDD？

类比思维：给 Agent 更长的系统提示，说明 TDD 的重要性。

第一性原理：
  分解：
  └─ 为什么 Agent 不遵循 TDD？
       ├─ 不是不理解，而是"用户要的是代码，不是测试"
       ├─ 跳过程序能得到即时满足（代码生成）
       └─ 遵循程序需要额外步骤，短期看不到回报
  └─ 基本事实：
       ├─ Agent 被训练成乐于助人 → 用户说"帮我实现"就会直接实现
       ├─ 即时满足 > 长期收益（对 Agent 来说）
       └─ 可选项越多，越容易选捷径

  从零重建：
  └─ 不是"告诉 Agent 要 TDD"
  └─ 而是"让 TDD 成为 Agent 唯一的路径"
  └─ 具体：先写测试 → 确认测试失败 → 才能写代码
  └─ 如果 Agent 想跳过程序 → 用 Cialdini 说服原则阻止
```

### 局限

| 局限 | 说明 |
|------|------|
| **耗时** | 每个问题都从零开始分解，不可持续 |
| **深度未知** | 不知道什么时候该停——可以一直分解下去 |
| **知识依赖** | 需要领域基础知识才能找到真正的"第一性" |
| **过度理性** | 并非所有问题都值得从零推理 |
| **效率** | 80% 的问题通过类比（复用经验）解决更高效 |

**平衡原则**：用第一性原理应对**非共识、高影响**的问题。日常决策依赖类比和经验。

## 2. 二阶思维

### 定义

| 提出 | 查理·芒格（Charlie Munger）推崇的思维模型 |
|------|------------------------------------------|
| 本质 | 每次决策后问自己：**"然后呢？再然后呢？"** |

### 层次

```
一阶思维（First-Order）：
  "我们加一个 retry 机制来处理超时错误。"
  → 结果：超时减少了，系统更稳定了。✓

二阶思维（Second-Order）：
  "加了 retry 机制...然后呢？
   重试可能掩盖了底层服务的性能问题。
   大量重试可能使问题恶化（重试风暴）。
   客户端感知的延迟反而增加了。
   我们应该先调查为什么超时，而不是直接加 retry。" ✗
```

### 在软件开发中的应用

| 决策 | 一阶效果 | 二阶效果 |
|------|---------|---------|
| 加入缓存 | 响应变快 | 缓存一致性问题、数据过期、调试困难 |
| 抽象一个通用组件 | 复用性提高 | 过度抽象、维护成本上升、未来变更困难 |
| 让 Agent 自动修复 bug | 节省时间 | Agent 可能引入新的 bug，没有理解根本原因 |
| 使用 monorepo | 共享代码方便 | 构建时间增长、权限管理复杂、工具链限制 |

### 二阶思维清单

```
在做出一个工程决策前，问自己：
  1. 这个决定的一个月后后果是什么？
  2. 这个决定的一年后后果是什么？
  3. 谁最不希望我做这个决定？他们为什么是对的？
  4. 如果每个人都这样做，会发生什么？
  5. 这个决定解决了当前问题，但创造了什么新问题？
```

## 3. 逆向思维

### 定义

| 提出 | 查理·芒格（Charlie Munger） |
|------|---------------------------|
| 名言 | "反过来想，总是反过来想。" — 卡尔·雅各比（数学家） |
| 本质 | 与其问"怎样成功"，不如问**"怎样避免失败"** |

### 核心方法

```
正面：我们应该怎么做才能让这个项目成功？
逆向：什么会导致这个项目必然失败？
       └── 列出所有可能的失败原因
           └── 逐一避免这些原因
               └── 避免失败 = 自然走向成功
```

### 在软件开发中的应用

| 正面问题 | 逆向问题 |
|---------|---------|
| 怎样提高代码质量？ | 什么会导致代码质量下降？→ 不加审查、不写测试 |
| 怎样让架构可扩展？ | 什么会导致架构僵化？→ 耦合过紧、抽象错误 |
| 怎样提高 Agent 遵循流程的概率？ | 什么会导致 Agent 跳过流程？→ 时间压力、捷径诱惑 |

### 将逆向思维用于 Skill 设计（Superpowers 实践）

```
目标：让 Agent 在调试时遵循系统化调试技能

逆向思考：什么会导致 Agent 跳过调试技能？
  └─ 时间压力（"生产宕机了"）
  └─ 自信（"我是这方面的专家"）
  └─ 已有方案在眼前

针对每个原因设计防护：
  └─ 时间压力 → "技能会帮你更快找到根因"
  └─ 自信 → "专家也会用清单"
  └─ 已有方案 → "跳过技能可能遗漏真正的根因"
```

## 4. 奥卡姆剃刀

### 定义

| 提出 | 威廉·奥卡姆（William of Ockham，14 世纪） |
|------|------------------------------------------|
| 原句 | "如无必要，勿增实体。"（Entities must not be multiplied beyond necessity.）|
| 本质 | 在多个解释中，最简单的那个通常是正确的（但不是必然） |

### 在软件开发中的应用

| 场景 | 复杂方案 | 简单方案 |
|------|---------|---------|
| 状态管理 | Redux + Saga + Reselect | useState + useContext |
| 部署 | Kubernetes + Istio + Prometheus | Docker Compose / 平台 PaaS |
| API 设计 | GraphQL + REST + WebSocket | REST（先）→ 按需扩展 |
| Agent 技能 | 一个技能处理所有场景 | 多个小技能，每个只做一件事 |

### 注意事项

- **不是"最简单的总是最好的"**，而是"不要增加不必要的复杂性"
- 在软件中，复杂性的增加应该是**有意识的、被证明必要的**，而不是预设的
- YAGNI（You Aren't Gonna Need It）是奥卡姆剃刀在软件开发中的具体体现

## 5. 能力圈

### 定义

| 提出 | 沃伦·巴菲特 & 查理·芒格 |
|------|------------------------|
| 本质 | 清晰知道自己的能力边界，在圈内做决策，圈外学习或合作 |

### 模型

```
          ┌─────────────────┐
          │   能力圈         │ ← 你真正懂的东西
          │  ┌───────────┐  │
          │  │ 专业知识    │  │ ← 深度掌握
          │  └───────────┘  │
          └─────────────────┘

          ┌─────────────────┐
          │   学习圈         │ ← 正在学习的东西
          │  你可以理解      │
          └─────────────────┘

          ┌─────────────────┐
          │   未知圈         │ ← 你完全不懂的东西
          │  聘请专家或合作  │
          └─────────────────┘
```

### 在软件开发中的应用

```
作为开发者，你的能力圈可能是：
  ├─ 圈内：你使用的语言和框架、你的业务领域
  ├─ 学习圈：你正在学习的新技术、相关领域
  └─ 未知圈：你从未接触过的领域

能力圈决策原则：
  └─ 圈内：直接决策 → 信心高
  └─ 学习圈：慢速决策 → 需要更多验证
  └─ 未知圈：不决策 → 找专家
```

### AI Agent 的能力圈

这个概念直接映射到 Agent Skills 中：

```
能力圈 = 安装的技能集合
  └─ 圈内：已安装技能覆盖的领域 → Agent 自动匹配
  └─ 圈外：没有对应技能 → Agent 会"猜测"（类比思维）

这就是 1% 规则的意义：
  "不要让你的 Agent 猜测，给它安装技能。"
```

## 6. 思维栅格

### 定义

| 提出 | 查理·芒格 |
|------|----------|
| 核心 | **单一思维模型的局限性**："对于一个只有锤子的人来说，所有问题看起来都像钉子。" |
| 解决 | 建立一个跨学科的"思维模型栅格"，用不同学科的工具解决不同问题 |

### 芒格的 100+ 模型

精选（对软件开发特别相关的）：

| 学科 | 模型 | 应用于软件 |
|------|------|-----------|
| **数学** | 复利效应 | 技术债的积累和偿还 |
|  | 概率思维 | 风险评估、技术选型的不确定性 |
|  | 帕累托法则（80/20） | 关注影响最大的功能/bug |
| **物理** | 临界点 | 系统过载的点 |
|  | 熵增 | 软件系统自然趋向混乱（需要主动维护） |
| **生物** | 进化论 | 架构演进、适者生存的 API 设计 |
|  | 多样性 | 团队的认知多样性提高决策质量 |
| **心理学** | 确认偏误 | 只看到支持自己观点的证据 |
|  | 沉没成本 | 继续投入一个已失败的项目 |
|  | 社会认同 | 跟风使用流行技术但不适合自己 |
| **经济学** | 机会成本 | 选择一项技术 = 放弃其他所有选择 |
|  | 边际效益递减 | 测试覆盖率从 80%→90% 的代价（20%→80%）|
| **工程** | 反馈回路 | CI/CD、监控、告警 |
|  | 冗余 | 系统的高可用设计 |
| **哲学** | 奥卡姆剃刀 | 保持简单 |
|  | 第一性原理 | 从零开始推理 |

### 在软件开发中的应用

```
当你遇到一个问题时：
  1. 识别问题所属的领域
  2. 从该领域选择最相关的思维模型
  3. 用该模型分析问题
  4. 如果不够，换一个模型

示例：团队交付速度变慢
  └─ 从心理学看：确认偏误 → 团队一直在用熟悉的方案
  └─ 从经济学看：边际效益递减 → 更多的优化投入产出比降低
  └─ 从工程看：反馈回路太长 → CI 时间太长
```

## 7. 帕累托法则

### 定义

| 提出 | Vilfredo Pareto（意大利经济学家，1906） |
|------|----------------------------------------|
| 核心 | **80% 的结果来自 20% 的原因** |

### 在软件开发中的应用

| 领域 | 80% 效果 | 20% 投入 |
|------|---------|---------|
| Bug | 80% 的用户可见问题 | 20% 的核心缺陷 |
| 功能 | 80% 的用户价值 | 20% 的核心功能 |
| 性能 | 80% 的性能提升 | 20% 的关键路径优化 |
| 代码 | 80% 的时间花在 | 20% 的复杂模块上 |
| Skill | 80% 的改善来自 | 20% 的关键技能 |

### 对 Agent Skill 设计的启示

```
不必一开始就覆盖所有场景。
首先识别最频繁、最影响质量的 20% 场景。
为这 20% 创建技能，就能覆盖 80% 的价值。

例如：
  高频使用技能：code review、commit message、test generation
  低频使用技能：deployment、migration、security audit
  先做高频的。
```

## 8. 汉隆剃刀

### 定义

| 提出 | 罗伯特·J·汉隆（Robert J. Hanlon） |
|------|-----------------------------------|
| 原句 | "能用愚蠢解释的，就不要归咎于恶意。" |
| 本质 | 优先假设他人失误而非故意破坏 |

### 在软件开发中的应用

```
bug 出现时：
  归因于恶意："这人是故意写烂代码。"
            → 造成对立和推诿

  归因于愚蠢/失误：
    "他可能没注意到这个边界情况。"
    "他可能不知道这个模式。"
    "测试没有覆盖到这种情况。"
    → 改进流程、代码审查、测试

在 Agent 行为中：
  Agent 跳过流程时：
    不是"Agent 不听话" → 而是"技能设计不够强，让 Agent 有路可逃"
```

## 9. KISS 原则

### 定义

| 全称 | Keep It Simple, Stupid |
|------|------------------------|
| 起源 | 美国海军（1960） |
| 本质 | 系统越简单，越容易理解、维护、修改和调试 |

### 在软件开发中的应用

```
反对过度工程（Over-engineering）：

  "我们可能需要用到分布式事务" → 现有单库就能解决吗？
  "这个应该抽象成一个通用框架" → 目前只有两个场景用
  "先用 Redis + PostgreSQL + Elasticsearch" → 一个 PostgreSQL 够吗？
```

### 与奥卡姆剃刀的区别

| 原则 | 侧重点 |
|------|--------|
| 奥卡姆剃刀 | 解释的简洁性 — 选择假设时 |
| KISS | 设计的简洁性 — 构建系统时 |
| YAGNI | 功能的简洁性 — 只做需要的 |

## 10. 过早优化是万恶之源

### 定义

| 提出 | 唐纳德·克努斯（Donald Knuth，1974） |
|------|-------------------------------------|
| 原话 | "过早优化是万恶之源。" |
| 本质 | 在没有性能数据之前进行优化，弊大于利 |

### 正确的顺序

```
1. 写出正确的代码 → 2. 测量性能 → 3. 如果有问题 → 4. 优化

跳过步骤 2 直接优化：
  └─ 可能优化了不重要的路径
  └─ 增加了代码复杂度
  └─ 降低了可读性
  └─ 可能引入新的 bug
```

### 将此原理用于 Skill 设计

```
不要预先设计一个覆盖所有场景的"万能技能"。
先写一个只覆盖最频繁场景的最小技能。
根据使用反馈逐步扩展。

这就是 Superpowers 的方法：
  └─ 14 个技能，每个只做一件事
  └─ 不提供"全能"技能
  └─ 通过技能组合覆盖复杂场景
```

## 11. 康威定律

### 定义

| 提出 | 梅尔文·康威（Melvin Conway，1967） |
|------|-----------------------------------|
| 原句 | "设计系统的架构受限于生产这些设计的组织沟通结构。" |
| 通俗 | **团队的沟通结构会反映在软件架构上** |

### 三个推论

```
1. 组织结构和系统架构趋于一致
    └─ 两个团队维护同一个模块 → 架构经常出问题

2. 独立的系统需要独立的团队
    └─ 微服务需要有对应的自治团队

3. 大系统需要大团队 → 大团队产生大架构
    └─ 想要简单的架构？先有简单的组织
```

### 逆康威定律（Inverse Conway Maneuver）

```
想要什么样的架构 → 就建立什么样的团队结构。

示例：
  想要微服务架构？
  └─ 组建 3 个独立团队（用户/订单/支付）
  └─ 每个团队有自己的发布管道
  └─ 架构自然走向微服务
```

### 对 AI Agent 设计的启示

```
类比到 Agent 技能设计：

  BMAD 方法：21 个角色 Agent = 组织结构
    └─ 每个角色独立的系统提示 ✓
    └─ 角色之间通过文件制品通信 ✓
    └─ 结果：架构自然模块化 ✓

  Superpowers 方法：14 个独立技能
    └─ 每个技能是独立的 "团队"
    └─ 技能间通过 design.md / plan.md 通信
    └─ 结果：技能可以独立演进 ✓
```

## 12. 古德哈特定律

### 定义

| 提出 | 查尔斯·古德哈特（Charles Goodhart，1975） |
|------|------------------------------------------|
| 原句 | "当一个指标成为目标时，它就不再是一个好的指标。" |
| 本质 | **人们会优化指标本身，而不是指标要代表的价值** |

### 在软件开发中的应用

```
指标恶化为目标的经典案例：

  1. Bug 数量："我们的目标是将 Bug 减少 50%。"
     → 结果：开发者不再报告 bug（bug 变少了！）

  2. 代码覆盖率："覆盖率必须达到 80%。"
     → 结果：团队写了很多没用的测试来凑覆盖率

  3. 提交次数："每人每天提交 5 次。"
     → 结果：大量无意义的小提交（"fix typo"）

  4. 行数（LOC）："以代码行数衡量生产力。"
     → 结果：代码膨胀、重复、不必要的抽象
```

### 对 Agent Skill 设计的启示

```
不要用"是否加载了技能"来衡量技能的有效性。

正确的度量：Agent 在相关场景下是否遵循了技能？

错误的度量：技能是否被加载？→ Agent 可能加载了但不遵循

更好的度量：
  └─ 压力场景测试通过率
  └─ 两阶段审查阻塞率
  └─ 人类审查满意度
```

## 13. 帕金森定律

### 定义

| 提出 | 西里尔·诺斯古德·帕金森（C. Northcote Parkinson，1955） |
|------|--------------------------------------------------------|
| 原句 | "工作会自动膨胀，以填满可用的完成时间。" |
| 本质 | **给多少时间，工作就会用掉多少时间** |

### 在软件开发中的应用

```
示例：
  └─ Sprint 有 2 周 → 2 周没有截止感
  └─ Sprint 有 1 周 → 1 周有紧迫感但仍然足够

对策：
  └─ 时间盒（Timebox）：固定时间，灵活范围（Shape Up）
  └─ 设定更小的时间单位
  └─ 先做最重要的（帕累托法则）

Shape Up 的 6 周周期 + 冷却期 就是对帕金森定律的回应：
  └─ 固定 6 周 → 工作自然适应这个窗口
  └─ 2 周冷却期 → 让未完成的工作有机会浮出水面
```

## 14. 布鲁克斯定律

### 定义

| 提出 | 弗雷德里克·布鲁克斯（Frederick Brooks，1975，《人月神话》） |
|------|------------------------------------------------------------|
| 原句 | "在一个已延期的项目中增加人手，只会让它更延期。" |
| 原因 | 新人需要培训时间 + 团队沟通成本指数增长 |

**沟通成本公式**：
```
n 个开发者 → 沟通通道数 = n(n-1)/2
5 人 → 10 条通道
10 人 → 45 条通道
20 人 → 190 条通道
```

### 对 AI Agent 设计的启示

```
类比：多个子代理并行执行

  ├─ 好处：每个子代理有完整的上下文窗口
  ├─ 成本：主代理需要协调、审查、合并
  └─ 平衡点：任务边界越清晰，并行收益越大

Superpowers 的子代理策略：
  └─ 每个任务独立 → 沟通成本 = 0（子代理之间不通信）
  └─ 主代理只做审查 → 沟通成本线性增长
  └─ 符合布鲁克斯定律的反面设计
```

## 15. 邓巴数

### 定义

| 提出 | 罗宾·邓巴（Robin Dunbar，1990s） |
|------|----------------------------------|
| 核心 | 人类能维持稳定社交关系的认知上限约为 **150 人** |
| 子层级 | 5（亲密）、15（信任）、50（熟悉）、150（社群）、500（名义）|

### 在软件开发中的应用

```
团队规模：
  └─ 2 个披萨团队（亚马逊）：6-8 人 → 在邓巴的 15 人信任圈内
  └─ Scrum 团队推荐：3-9 人 → 也在信任圈内
  └─ 超过 20 人 → 需要分拆

代码库规模：
  └─ 一个开发者能有效维护的代码量约为 10-15K 行（经验法则）
  └─ 超过时需要考虑分模块
```

### 对 Agent 设计的启示

```
Agent 的"认知上限"是上下文窗口（目前约 1M tokens）。
超过这个上限 → Agent 的性能显著下降。

技能的设计就是"分而治之"：
  └─ 每个技能是 Agent 的一个"熟人"
  └─ Agent 不需要同时认识所有人（所有技能）
  └─ 只需在需要时加载相关的技能
```

## 16. 因果漏斗：从原理到决策

```
问题
  │
  ├── 用第一性原理分解到底层事实
  │     │
  │     ├── 确认基本事实和不可变约束
  │     │
  │     ├── 挑战所有"因为以前就这样"的假设
  │     │
  │     └── 识别：哪些是真正的约束？哪些是过时的惯例？
  │
  ├── 用二阶思维推演后果
  │     │
  │     └── "如果这样做，接下来会发生什么？再发生什么？"
  │
  ├── 用逆向思维检查
  │     │
  │     └── "什么会导致失败？如何避免？"
  │
  └── 最终决策，保持简单（KISS / 奥卡姆）
```

## 附录：思维模型速查表

| 当你面临... | 用这个模型 | 问自己 |
|-----------|-----------|--------|
| 一个复杂问题 | **第一性原理** | 最基本的组成是什么？ |
| 一个决策的后果 | **二阶思维** | 然后呢？再然后呢？ |
| 不知道该做什么 | **逆向思维** | 怎样会失败？避免它。 |
| 系统越来越复杂 | **奥卡姆剃刀** | 这个真的必要吗？ |
| 不确定该不该做 | **能力圈** | 这是我的领域吗？ |
| 跟别人争论 | **汉隆剃刀** | 可能是失误不是恶意？ |
| 想设计一个系统 | **康威定律** | 团队结构会如何影响它？ |
| 设置团队目标 | **古德哈特定律** | 这个指标会不会被玩弄？ |
| 估算工作量 | **帕金森定律** | 时间给多了还是少了？ |
| 项目延期了 | **布鲁克斯定律** | 加人真的有效吗？ |
| 想做很多功能 | **YAGNI / KISS** | 现在真需要这个吗？ |
| 想提前优化 | **克努斯定律** | 有数据证明这里慢吗？ |
| 看到 Agent 不听话 | **第一性原理** | 什么基本机制能让它听话？ |
| 不知道 Agent 该知道什么 | **能力圈** | 给它装什么技能覆盖这个域？ |
| Agent 做出怪异决定 | **汉隆剃刀** | 可能是技能设计问题，不是 Agent 问题 |
